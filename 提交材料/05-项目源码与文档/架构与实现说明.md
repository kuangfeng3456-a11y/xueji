## 2. 32 个测试失败的根因分析

失败**不是随机损坏，而是同一次架构升级的遗留**。按根因分五组：

### 组 1 · 掌握度算法 v1 → v2 升级（约 14 个失败，占 44%）

失败信息反复出现 `assert 0.08 == 0.3`：

- v1 公式 `m_new = m + 0.3 × (r − m)`，初始 m=0 答对 → **0.3**
- v2 `bkt_update()`（贝叶斯后验 + `BKT_LEARN=0.08` 学习转移 + 证据加权 + ±0.30 防抖），同场景 → **0.08**

代码已切到 v2（`mastery_service.apply_answer()` 调用 `bkt_update`），但 `test_flashcards.py`、`test_api_learning.py`、`test_mastery_rhythm.py`、`test_probes.py`、`test_quiz.py`、`test_api_ai_lab.py` 仍在断言 v1 的 0.3。**这是测试该改，不是代码该回退。**

### 组 2 · 证据链 payload 新增字段（3 个失败）

`test_evidence.py`、`test_freshness.py` 用 `==` 精确比对整个 dict，而 `record_evidence` 现已写入 `engine`、`snapshot_id`、`evidence_version`、`chosen` 等新字段。断言写法过严，应改为子集校验。

### 组 3 · LLM 客户端 mock 方式变化（3 个失败）

- `test_ai_content.py:151`：`TypeError: object MagicMock can't be used in 'await' expression`——`llm.chat_json` 已是 async，测试用了同步 MagicMock，需改 `AsyncMock`
- `test_llm.py:66,85`：期望返回文案却得到 `None`，熔断或缓存路径变了

### 组 4 · 接入状态与降级判定变化（6 个失败）

`test_integrations.py` 多处 `assert 'degraded' == 'ok'`、`assert 'ok' == 'unavailable'`、`assert 2 == 1`——探活项数量与状态枚举已扩展，测试未跟进。

### 组 5 · 其他行为变更（约 6 个失败）

- `test_quiz.py:298`：`DID NOT RAISE ValueError`——父知识点校验被移除或改为返回错误码
- `test_probes.py:230`：探针 kind 枚举新增 `reverse`，测试断言的元组过期
- `test_panel.py:207`、`test_api_core.py:274`：字段结构变化

### 修复优先级建议

| 优先级 | 动作 | 预计影响 |
|--------|------|----------|
| P0 | 组 1：把 14 处 `0.3` 断言改为 BKT 期望值（或改为断言"掌握度上升"而非精确值） | 消除 44% 失败 |
| P0 | 组 3：`MagicMock` → `AsyncMock` | 3 个 |
| P1 | 组 2：精确 dict 比对 → 子集/关键字段比对 | 3 个 |
| P1 | 组 4：按当前探活项重写期望 | 6 个 |
| P2 | 组 5：逐个确认是行为变更还是真 bug（`test_quiz.py:298` 的 DID NOT RAISE 需人工判断校验该不该存在） | 6 个 |
| P0 | 重跑 `run_coverage.py` 覆盖全部 144 个文件，重新生成报告；建议同时用 `coverage.py` 交叉验证 | 恢复交付材料可信度 |

> 组 5 中的 `DID NOT RAISE` 和 `test_integrations` 的状态断言**有可能是真实回归**，不能一律当作"测试过期"处理，需逐个确认业务预期。

## 3. 系统架构

```
浏览器 (Vue 3 SPA · Hash 路由 · 自建 Rollup 构建)
   │  fetch → /api  (Bearer JWT)
   ▼
FastAPI  ── 中间件：cache_control / access_log(request_id)
   │        异常处理：SQLAlchemyError→503、Exception→500
   ├─ api/       35 个路由模块 · 120 端点 · 115 需鉴权
   ├─ agents/    Planner / Diagnoser / Coach / Reporter（规则内核 + 可选 LLM 润色）
   ├─ services/  60+ 模块：规则引擎、排程、诊断、洞察、模拟、RAG…
   ├─ rules.py   ★ 纯函数规则层，零 DB 依赖，可独立单测
   ├─ llm.py     OpenAI 兼容 · 熔断 · 双网关 fallback · SHA256 语义缓存
   └─ cache.py   Redis / 内存双后端，双写，失败静默回退
   ▼
MySQL(RDS) ⇄ SQLite 降级     DCS Redis ⇄ 内存缓存降级     OBS(仅配置项)
```

### 3.1 四智能体的真实形态

**结论：不是多智能体协作，而是同一规则引擎的四个功能出口，各带一层可选 LLM 文本增强。**

| Agent | LLM 用在哪 | 无 Key 时 |
|-------|-----------|----------|
| Planner | 仅润色 summary（≤70 字今日重点） | 排程结果完整，summary 保留规则原文 |
| Diagnoser | 语义归因，输出 `{category, suggestion}` 并做枚举校验 | `classify_mistake` 规则链 |
| Coach | 可选重写提醒文案（≤80 字） | `_rule_message` 四分支模板 |
| Reporter | 追加 ≤120 字教练点评 | 模板拼接完整周报 |

四者之间**无消息传递、无任务委派、无共享工作记忆**，无 orchestrator。`AgentRun` 表是审计日志，不是协作协议。答辩时若被追问"多智能体如何协作"，应据实说明为"职责分离的规则内核 + 统一 LLM 增强层"，不宜宣称 agent-to-agent 协作。

### 3.2 LLM 降级链路（设计扎实）

```
调用 → 语义缓存命中? → 返回
     → HTTP(25s 超时) → 成功 → 写缓存 + 重置失败计数
                      → 失败 → 有 fallback 网关? → 尝试 fallback（独立计数）
                                            → 无 → 返回 None → Agent 走规则路径
连续失败 ≥3 次 → 熔断 60s（期间 available=False，不触发 fallback）
```

局限：熔断状态是**进程级内存变量**，多实例部署不共享；`chat_json()` 用正则 `\{.*\}` 提取 JSON，对嵌套或多段 JSON 不稳健。

### 3.3 数据库降级

`config.py` 优先级：`RDS_*_HOST` > `DATABASE_URL` > 本地 SQLite。`database.py` **仅在启动时** `SELECT 1` 探活一次，失败则 `dispose()` 并切 SQLite，置 `ACTIVE_DATABASE_BACKEND="sqlite-fallback"`、`DATABASE_FALLBACK=True`，经 `/api/health` 与 `/api/integrations` 暴露。

**降级是单向的**：运行期间 RDS 恢复不会自动切回，需重启。

## 4. 核心算法（以代码为准）

### 4.1 README 公式对账

| 规则 | README 描述 | 代码实际 | 一致性 |
|------|------------|----------|--------|
| 掌握度更新 | `m + 0.3×(r − m)` | v1 `update_mastery()` 一致但**已不在主流程使用**；主流程走 v2 `bkt_update()` | ⚠️ **README 过时** |
| 复习间隔 | `1/2/4/7/15` 天，答错回 1 天 | `REVIEW_INTERVALS=[1,2,4,7,15]`，答对 stage+1（上限 4），答错 stage=0 | ✅ |
| 任务优先级 | `权重 × (1−掌握度) × 临近系数` | 一致，另有安全下限 `weight=max(w,0.1)`、`max(1−m,0.05)` | ✅ |
| 临近系数 | `1 + 3×e^(−剩余天数/14)` | 完全一致 | ✅ |
| 错题补救 | 同知识点 7 天内 ≥2 道 → 插入 20 分钟补救 | 一致，`REMEDIAL_MINUTES=20`，最多取前 2 个知识点 | ✅ |

### 4.2 v2 算法（README 未记载，但已实现）

| 算法 | 公式 | 关键常量 |
|------|------|----------|
| BKT-lite | 答对 `posterior = m(1−slip)/[m(1−slip)+(1−m)·guess]`；答错 `posterior = m·slip/[m·slip+(1−m)(1−guess)]`；`m_bkt = posterior + (1−posterior)×learn`；`m_new = m + ew×(m_bkt−m)`，限幅 ±0.30 | `guess`: choice 0.25 / blank 0.10 / short 0.05；`slip=0.15`；`learn=0.08` |
| 置信度 | `c = 1 − e^(−n_eff/3)` | — |
| 不确定性 | `u = √[m(1−m)/(n_eff+2)]` | Laplace 平滑 +2 |
| 保持率 | `R(t) = 0.9^(t/S)` | 底数 0.9 |
| 稳定度 | 答对 `S' = S×(1.7 + 2×(1−R))`；答错 `S' = max(1, 0.4×S)` | — |
| 收益密度 | `V = w·[(1−m) + 0.6×(1−R) + 0.3×u]·U(d)·G`；`ρ = V/minutes` | λ_forget 0.6、λ_uncertainty 0.3 |
| 期望增益 | `ΔE = 100·w·η·(1−m)·G` | η: study .25 / practice .18 / review .10 / remedial .28 / mock .12 |
| 先修门控 | 任一先修掌握度 <0.5 → `G=0.5`，否则 `G=1.0` | 阈值 0.5 |
| 准备度 | `score = coverage×100 − max(0,load_ratio−1)×25 − gaps×4 − overdue×3 − violations×2`，clamp[0,100] | coverage = Σ(w·m)/Σw |
| 风险五因子 | forget .30 / prereq .25 / error .20 / transfer .15 / overdue .10；置信度 `min(0.95, 0.2+0.06×n)` | n<3 标 insufficient |
| 认知负荷 | `load = fatigue×0.55 + max(0,今日分钟/计划分钟−1)×35 + 错题率×25` | ≥80 overload / ≥55 high / ≥30 optimal |
| 疲劳指数 | 离开页面×8 + 中断×14 + 超180min部分×0.12 + 错题周增长×6 + 违约×5 + 长连续×1.2，上限 100 | — |
| 蒙特卡洛 | 1000 次采样，`seed=42` 可复现，输出 p10/p50/p90 与达标概率 | — |
| 扰动度 | `D = 被移动任务数 / 未来7天任务总数`，D>0.3 需用户确认 | — |
| 节奏自适应 | 近 28 天完成率 <50% 且样本 ≥6，或平均延迟 ≥2 天且样本 ≥3 → 每日任务 3 降为 2 | — |
| RAG 排序 | 段落 ≤400 字切块，`|Q∩C|/|Q|` bigram 重叠率降序 | — |

### 4.3 已发现的算法一致性缺陷

**`forecast.py` 使用独立参数体系，与 `rules.py` 未对齐**：

| 参数 | forecast.py | rules.py | 问题 |
|------|-------------|----------|------|
| 学习增益 | `GAIN_PER_TOUCH=0.12` | `BKT_LEARN=0.08` | 两套增益模型 |
| 遗忘 | `DAILY_FORGET=0.995`（线性乘） | `R(t)=0.9^(t/S)`（指数保持率） | 两种遗忘模型 |

后果：冲刺模拟器给出的"考试日掌握度预测"与实际掌握度更新逻辑不是同一套数学，预测值与用户真实掌握度轨迹会系统性偏离。答辩若被追问"预测怎么算的、和掌握度模型什么关系"，这是软肋。建议统一到 `rules.py` 的保持率模型，或明确说明 forecast 是独立的粗粒度情景模型。

## 6. API 设计

120 个端点，115 个需 Bearer Token，仅 `register`/`login`/`skills`/`meta`/`health` 公开。归属校验通过 `get_user_goal()` 与手动 `owner_id` 比对实现，**无 RBAC**（教师端权限靠"班级创建者"判定）。

### 6.1 需要修的设计问题

| 问题 | 位置 | 说明 |
|------|------|------|
| **GET 端点内做写操作** | `GET /api/dashboard` | 内部调用 `auto_adjust_today()`，会 replan/build_plan/commit，违反幂等语义；爬虫预取或前端重试都可能意外改计划 |
| **用 ValueError 做归属校验** | `api/risk_forecast.py` 三个端点 | 越权访问返回 **500** 而非 403/404，泄漏内部错误且语义错误 |
| **资源路径风格不一致** | 全局 | `goals`/`gaps`/`probes`/`mistakes`/`experiments` 有的嵌套在 `/goals/{id}/` 下，有的走顶层；PATCH/PUT/POST 混用 |
| **仅 1 处限流** | `POST /api/goals/{id}/mistakes`（30 次/分钟） | 登录、注册、计划生成、LLM 类端点**全部无限流**，可被暴力破解或刷爆 token 费用 |
| **列表端点缺分页** | 多处 | 错题、任务、证据链等直接全量返回 |
| **上传大小限制未生效** | `MAX_UPLOAD_BYTES=5MB` | 常量已定义但部分上传路径未引用校验（`/focus/{id}/snapshot` 有校验，其余需逐个确认） |

## 7. 前端

### 7.1 自建构建链（`build.mjs`）

项目**同时存在** `build.mjs` 和残留的 `vite.config.js`，但 `package.json` 的 build 指向 `node build.mjs`，且 vite 未在 dependencies 中——Vite 配置是废弃文件。

| 维度 | 现状 | 风险 |
|------|------|------|
| SFC 编译 | 自写 `vuePlugin()`，手动串 `parse → compileScript → compileTemplate → rewriteDefault` | 🔴 Vue 升级时编译器 API 变更即失效 |
| 代码压缩 | **未配置任何 minifier**，产物 `app.js` 1.1 MB | 🔴 首屏性能 |
| 代码分割 | `inlineDynamicImports: true`，33 个页面打进单文件 | 🔴 无路由级懒加载 |
| CSS | `.css` transform 返回空模块，`style.css`（5103 行）原样拷贝，无 PostCSS/autoprefixer | 🟡 旧浏览器兼容 |
| 缓存 | SHA-256 前 10 位作**查询参数** `?v=xxx`，非文件名哈希 | 🟡 依赖服务端正确响应 |
| Sourcemap | `false` | 🟡 线上排错难 |
| HMR | 无 | 🟡 开发体验 |

### 7.2 应用结构

- **状态管理**：自研 `reactive()` store，非 Pinia/Vuex。无 action 约束，任何组件可直接改任意字段
- **Token**：存 `localStorage('xueji_session')` 明文 JSON。401 时自动清 session 跳登录
- **API 层**：`api.js` 基于原生 fetch，约 90 个方法。**无超时、无 AbortController、无重试、无并发控制** → 网络挂起时 UI 无限等待；页面快速切换时旧请求回来会更新已卸载组件
- **路由守卫**：仅检查本地 token 是否存在，不校验有效性

### 7.3 页面完整度

33 个页面中 **29 个完整、4 个基本可用**（Skills / DocumentLibrary / TeacherDesk / ParentReport，均 146-247 行）、**0 个占位骨架**。全部有空状态与加载态。

### 7.4 值得肯定的部分

## 8. 创新模块实现深度评级

28 个模块逐个评级（详见 `04_innovation_services.md`）：

| 评级 | 数量 | 模块 |
|------|------|------|
| **扎实** | 16 | knowledge_map、simulation、cognitive_load、risk_forecast、panel、twin、experiments、insights、psychology、rag、advanced、lsv、entertainment、knowledge_base、evidence、learning_events |
| **中等** | 9 | knowledge_graph、freshness、probes、tutor、teacher、eval_center、wellbeing、synthetic、social、qa |

| **空壳** | 0 | — |

### 8.1 冷启动问题（重要）

**8 个模块在用户无学习记录时输出全 0 或默认值，不具诊断价值**：simulation、risk_forecast、cognitive_load、insights、twin、experiments、panel、knowledge_map。

具体表现：`risk_forecast` 五因子全 0 → risk_score≈0 且全部标 insufficient；`cognitive_load` fatigue=0、wrong_ratio=0 → 永远输出 "low"；`insights` 热力图全 0、雷达五维全 0、徽章全未解锁。

需 1-2 周持续使用才有意义。**建议在前端明确标注冷启动期**（如"数据积累中，需完成 N 次练习后开启诊断"），否则新用户首次进入这些页面会看到一片 0，体验很差，答辩演示也必须用有数据的账号。

### 8.2 跨模块重复实现（应重构）

四个工具函数被各自独立实现 4-5 遍，逻辑完全相同：

| 函数 | 重复位置 |
|------|----------|
| 叶子知识点筛选 `_leaves()` | knowledge_map、simulation、risk_forecast、probes、twin（另 flashcards:14、quiz:18、planner:58） |
| 掌握度映射 `_mastery_map()` | knowledge_map、risk_forecast、probes、twin、readiness（另 planner:44、schedule_preview:37） |
| 错题计数 `_mistake_counts()` | knowledge_map、probes、readiness |
| 先修链 BFS | `knowledge_map.prerequisites()` 与 `risk_forecast._prereq_chain()` 逻辑相同仅函数名不同 |

建议抽到公共模块（`rules.py` 或新建 `helpers.py`）。当前状态是维护风险：改一处忘改其余，会产生行为不一致。

### 8.3 性能热点（N+1 与重复全量查询）

| 位置 | 问题 |
|------|------|
| `planner.py:464-474` | replan 时长溢出推迟时，对每一天单独 `select(Task).where(day==target)`，最坏 8×N 次查询 |
| `planner.py:411-413` | 冲刺段排序 candidates 时对每个叶子节点单独查 Mastery |

### 8.4 异常吞噬（最需警惕的质量问题）

### 10.1 规模与结构

### 10.2 隔离设计（值得肯定，防御纵深充分）

| fixture | 机制 |
|---------|------|
| `fresh_database`（autouse） | 每用例前后 `drop_all` + `create_all`，内存 SQLite，并清空 `cache._fallback._data` |

### 10.3 覆盖率工具的可信度问题

`run_coverage.py` 基于标准库 `trace` 自研，不是 `coverage.py`：

| 维度 | 评价 |
|------|------|
| 同步代码 | ✅ 可靠 |
| 异步代码 | ⚠️ 部分可靠。已设 `threading.settrace`，但 `asyncio.run()` 在新线程跑协程，tracer 可能丢失部分异步路径 |
| 未导入模块 | ❌ **无法统计**。`trace` 只记录被执行到的行，这与 coverage.py 的 `--source` 模式有本质区别 |
| 分支覆盖 | ❌ 不支持，仅行覆盖 |

**后果**：现有报告只列出 29 个文件（项目实有 144 个），`simulation.py`、`readiness.py`、`knowledge_map.py`、`probes.py`、`panel.py`、`freshness.py`、`cognitive_load.py`、`api/ai_lab.py`、`api/cockpit.py` 等创新模块**根本不在统计范围内**。97.90% 这个数字对已覆盖的 29 个文件可信，但**不能代表项目整体覆盖率**。

建议：改用 `coverage.py --source=app` 重测，把真实数字写进 README；如坚持自研工具，需在文档中说明统计范围限定。

### 10.4 测试质量问题（除 32 个失败外）
